Unauthenticated SSRF in a WordPress plugin import endpoint

Example Plugin Vendor · example-plugin v1.2.3 · 2026-07

This is a demonstration post showing the layout. Replace it with a real writeup, or delete the file and remove its entry from assets/js/data/writeups.js.

Summary

The plugin exposed an import endpoint that accepted a URL parameter and fetched it server side. The handler was registered on a hook reachable without a session, and it performed no capability check and no validation of the supplied URL. Any unauthenticated visitor could make the WordPress host issue arbitrary outbound HTTP requests, including to internal addresses that are not reachable from the internet.

Affected Component

The import handler, registered for both the authenticated and unauthenticated AJAX hooks. Registering the unauthenticated variant is what turned an admin-only feature into a public one.

Root Cause

Three separate failures line up here. The handler is exposed to unauthenticated callers, it never calls a capability check, and it passes attacker input straight into the HTTP client. 

add_action( 'wp_ajax_plugin_import',        'plugin_import' );
add_action( 'wp_ajax_nopriv_plugin_import', 'plugin_import' );  // reachable with no session

function plugin_import() {
    // no current_user_can(), no check_ajax_referer()
    $url  = $_REQUEST['url'];
    $body = wp_remote_retrieve_body( wp_remote_get( $url ) );
    echo $body;
    wp_die();
}

Impact

An unauthenticated attacker can reach services that are only listening on the internal network: cloud instance metadata endpoints, admin panels bound to localhost, and internal APIs that trust their network position instead of authenticating callers. Because the response body is echoed back, this is a full read SSRF rather than a blind one, so the attacker sees the results directly.

Proof of Concept

A single unauthenticated request is enough to confirm it:

curl -s 'https://target.tld/wp-admin/admin-ajax.php' \
     --data 'action=plugin_import&url=http://169.254.169.254/latest/meta-data/'

The response contains the metadata listing, served by an address that is not routable from the attacker's own network. That confirms the fetch happened server side.

Recommended Fix

Drop the unauthenticated hook, add a capability check and a nonce, and validate the URL against an allowlist rather than trying to blocklist internal ranges. 

add_action( 'wp_ajax_plugin_import', 'plugin_import' );  // authenticated only

function plugin_import() {
    check_ajax_referer( 'plugin_import' );
    if ( ! current_user_can( 'manage_options' ) ) {
        wp_die( '', '', 403 );
    }
    $url = esc_url_raw( $_REQUEST['url'] );
    if ( ! plugin_host_is_allowed( $url ) ) {
        wp_die( '', '', 400 );
    }
    // ...
}

Blocklisting is the wrong instinct here. Decimal encoded addresses, IPv6 mapped forms, and DNS records that resolve to loopback all defeat naive filters, and a redirect from an allowed host walks straight past a check performed only on the initial URL.
