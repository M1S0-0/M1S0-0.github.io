Unauthenticated SSRF in a WordPress plugin import endpoint

An import handler that never checked who was calling it, and happily fetched any URL I handed over.

This is a demonstration article showing the layout. Replace it with a real writeup, or delete the file and remove its entry from assets/js/data/writeups.js.

Plugins that import data are worth a second look. Importing means fetching, fetching means the server makes a request on your behalf, and somewhere in that chain there is usually a URL that came from the user. The interesting question is never whether the plugin fetches things. It is who is allowed to ask it to.

In this case the answer turned out to be everyone.

Finding it

WordPress routes AJAX through a single entry point, and handlers register themselves against one of two hooks. One is for logged in users. The other is for everybody else. Grepping a plugin for the second one is a thirty second job and it is where I start. 

add_action( 'wp_ajax_plugin_import',        'plugin_import' );
add_action( 'wp_ajax_nopriv_plugin_import', 'plugin_import' );  // no session required

That second line is the whole story. The handler was written for administrators, and registering the unauthenticated variant turned an admin feature into a public one. That alone is not a vulnerability. What the handler does next is.

The bug

Three failures stack up here, and any one of them being absent would have made this a much less interesting report. 

function plugin_import() {
    // no current_user_can(), no check_ajax_referer()
    $url  = $_REQUEST['url'];
    $body = wp_remote_retrieve_body( wp_remote_get( $url ) );
    echo $body;
    wp_die();
}

There is no capability check, so being unauthenticated does not matter. There is no nonce, so it cannot even be argued that a request had to originate from the site. And the URL goes straight from the request into the HTTP client with no validation at all.

The response body is echoed back to the caller. That is the difference between a blind SSRF you have to infer and a read SSRF you can simply look at.

Why it matters

An SSRF is only as interesting as what the server can reach that you cannot. On a typical cloud host that list is longer than people expect: instance metadata endpoints handing out credentials, admin interfaces bound to localhost because binding to localhost felt like security, and internal APIs that authenticate callers by network position rather than by identity.

Because the body comes back in the response, none of this requires inference. You ask for a URL and you read what the server read.

Proof of concept

One unauthenticated request is enough:

curl -s 'https://target.tld/wp-admin/admin-ajax.php' \
     --data 'action=plugin_import&url=http://169.254.169.254/latest/meta-data/'

The response contains the metadata listing. That address is link local, so it is not routable from my network at all. Getting content back from it proves the fetch happened server side, which is the only thing the report actually needs to demonstrate.

The fix

Drop the unauthenticated hook, add a capability check and a nonce, and validate the URL against an allowlist. 

add_action( 'wp_ajax_plugin_import', 'plugin_import' );  // authenticated only

function plugin_import() {
    check_ajax_referer( 'plugin_import' );
    if ( ! current_user_can( 'manage_options' ) ) {
        wp_die( '', '', 403 );
    }
    $url = esc_url_raw( $_REQUEST['url'] );
    if ( ! plugin_host_is_allowed( $url ) ) {
        wp_die( '', '', 400 );
    }
    // ...
}

The instinct most people have here is to blocklist internal ranges instead. It does not hold up. Decimal encoded addresses, IPv6 mapped forms, and DNS records that resolve to loopback all walk past naive filters. Worse, a redirect from a host that passed the check lands you right back where you started, because the check ran once on the initial URL and never again on where it actually went.

Allowlist the hosts you meant to support. It is a shorter list than the internet.
