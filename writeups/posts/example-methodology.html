How I actually read a smart contract for the first time

Not line by line from the top. Here is the order I go in, and why invariants come before implementation.

Demonstration article. Replace with a real writeup, or delete the file and its entry in assets/js/data/writeups.js.

The first contest I entered, I opened the largest contract in the repo and started reading at line one. Four hours later I understood the code perfectly and had found nothing. Understanding the code is not the job. Understanding what the code is promising is the job, because a bug is a broken promise and you cannot spot one until you know what was promised.

Start with the money

Before any implementation, I answer three questions. Where does value enter the system, where does it leave, and who is allowed to move it while it is inside.

Those three answers give you a map of every function that matters. Everything else is plumbing you can read later, if at all. Most contests are won in the functions that appear in those answers.

Write the invariants down

An invariant is a sentence that should be true after every possible transaction. Total shares always match total deposits. Nobody withdraws more than they put in. Fees never exceed the configured maximum.

Write them in plain English before you write a single test. If you cannot state the invariant, you cannot recognise the transaction that breaks it.

This is also where you find the bugs nobody else does, because the interesting ones live in invariants the developers never wrote down either.

Then read for the gap

Now the implementation reading has a purpose. You are not asking whether the code is correct in the abstract. You are asking one narrow question per function: can I get this to violate one of my sentences.

That reframing changes what you notice. A few things start to look loud:

  • Arithmetic where the operand order assumes something about which value is larger
  • State written after an external call rather than before
  • Rounding that always lands the same direction
  • Any check that runs once on an input that can change afterwards
  • Access control that guards the obvious function and not its internal twin

Prove it before you believe it

The gap between this looks wrong and this is wrong is where most invalid submissions live. A test that fails is the only thing that closes it.

Writing the proof of concept also has a habit of killing the finding, which is the point. Better to lose it on your own machine than in triage.
