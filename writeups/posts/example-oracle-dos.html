One future-dated oracle round froze an entire vault

A timestamp subtraction nobody thought twice about, and the unsigned integer underflow that turned it into a denial of service.

Demonstration article. Replace with a real writeup, or delete the file and its entry in assets/js/data/writeups.js.

Staleness checks are boilerplate. Every protocol that reads a price feed has one, they all look roughly the same, and after you have read forty of them your eyes start to slide past. That is exactly why this one was worth stopping on.

The pattern

The contract reads the latest round from a feed and refuses to use a price that has gone stale. Reasonable. Here is the check. 

( , int256 answer, , uint256 updatedAt, ) = feed.latestRoundData();

require(answer > 0, "bad price");
require(block.timestamp - updatedAt <= MAX_AGE, "stale price");

Read that subtraction again. It assumes updatedAt is in the past. Every reasonable timestamp is. The question is what happens when one is not.

The bug

Solidity 0.8 reverts on arithmetic underflow rather than wrapping. So if updatedAt is even one second ahead of block.timestamp, the subtraction does not produce a huge number that fails the staleness check. It reverts outright, and it reverts before the check has a chance to say anything useful.

The guard against a bad price becomes the thing that breaks when the price is bad.
Note

Before Solidity 0.8 this would have wrapped to an enormous number and been caught by the staleness check on the very next line. The compiler upgrade that made arithmetic safer is what turned this into a denial of service.

Every function that reads the price inherits that revert. Deposits, withdrawals, liquidations, share accounting. All of them go through the same helper, so all of them stop at the same instant.

Why it matters

The window is short and it closes on its own, which is what makes the severity argument interesting rather than obvious. It lasts exactly as long as the drift between the pushed timestamp and block time, and then the chain catches up and everything resumes.

Short is not the same as harmless. A user cannot withdraw during it, and more importantly a liquidation cannot execute during it. A denial of service that reliably lands on the liquidation path during volatility is not a minor inconvenience, it is a solvency question.

Proof of concept

A mock feed with a timestamp a few seconds ahead is enough to show the revert, and it isolates the arithmetic from everything else in the system. 

function testPocFutureRoundFreezesVault() public {
    // push a round dated one minute into the future
    feed.setRound(1e8, block.timestamp + 60);

    vm.expectRevert();               // panic 0x11, arithmetic underflow
    vault.deposit(1 ether);

    // it resolves on its own once the chain catches up
    vm.warp(block.timestamp + 61);
    vault.deposit(1 ether);          // succeeds
}

The second half matters as much as the first. Showing that the condition clears is what tells a triager you understand the real severity, and it stops the report from being read as an overclaim.

The fix

Compare before subtracting, so a future timestamp is a rejected input rather than a revert.

require(updatedAt <= block.timestamp, "future round");
require(block.timestamp - updatedAt <= MAX_AGE, "stale price");

Two lines, and the failure mode goes from an unexplained panic that takes the whole protocol down to a named error on a single call.

Key takeaways

  • Every unsigned subtraction is an assumption about ordering. Find the one that can be violated.
  • Grep for block.timestamp - and - updatedAt across any protocol reading a feed.
  • Show the condition clearing as well as triggering. It is what separates a real severity argument from an overclaim.
  • A short denial of service on the liquidation path is a solvency issue, not an inconvenience.
